## 🛠️ 챗봇 서비스 구축 과정 (처음부터 끝까지)

> 프로젝트 세팅부터 완성까지, 코드가 만들어지는 순서 그대로 기록. 각 단계마다 "무엇을 만들었고, 왜 이 구조로 만들었는지"를 같이 정리.

### 1단계 — 프로젝트 초기 세팅

**한 것**
1. 새 폴더 생성
2. uv로 프로젝트 초기화
   ```bash
   uv init --bare --python 3.13
   ```
3. `requirements.txt`에 `streamlit` 추가
4. 라이브러리 설치
   ```bash
   uv add -r .\requirements.txt
   ```
5. `.python-version` 파일 생성 → 내용: `3.13`
6. `pyproject.toml`에서 streamlit 버전 고정
   ```toml
   [project]
   dependencies = [
       "streamlit == 1.61.1",
   ]
   ```

**결과물 폴더 상태 (예상)**
```

├── .python-version
├── pyproject.toml
├── requirements.txt
├── uv.lock
├── .venv/
└── app.py   (다음 단계에서 작성 시작)
```

**다음 단계**: `app.py`에서 챗봇 서비스 개발 시작

### 2단계 — 챗봇 기본 화면 (제목 + 채팅 메시지 UI)

```python
import streamlit as st

st.title("ChatBot Service") #서비스 제목

#사용자가 쓴 글 프린트하기
with st.chat_message("user"):
    st.markdown("코딩 너무좋아")
```

**한 일**
- `st.title()`로 서비스 제목 표시
- `st.chat_message("user")`로 "사용자가 보낸 메시지"처럼 보이는 UI 박스를 만들고, 그 안에 `st.markdown()`으로 텍스트 내용을 채움

**결과**: 카카오톡 말풍선처럼 생긴 UI 안에 "코딩 너무좋아"라는 텍스트가 표시됨 (지금은 하드코딩된 고정 텍스트, 실제 사용자 입력은 아직 아님)

### 3단계 — assistant 메시지 추가 + 사용자 입력받기 시작

```python
import streamlit as st

st.title("ChatBot Service") #서비스 제목
'''
#사용자가 쓴 글 프린트하기
with st.chat_message("user"):
    st.markdown("코딩 너무좋아")
    '''

#컴퓨가 쓴 글 프린트하기
with st.chat_message("assistant"):
    st.markdown("코딩이 그렇게 좋아?")

#위 코드만 두면 질문했을때 답을 주는게 아니라 독립적으로 그냥 프린트하는거임.

#사용자 답변
user_input = st.chat_input("매시지를 입력해주세요.") #chat_input은 사용자의 답변을 str로 리턴해줌
if user_input: #user_input이 있다면
    with st.chat_message("user"):
        st.markdown("user_input") #요렇게 사용자 글을 적어주는 거임.
```

**한 일**
- 2단계에서 만든 `user` 메시지 블록을 3중따옴표(`'''`)로 감싸서 **주석 처리**(잠깐 꺼둠)
- `st.chat_message("assistant")`로 AI가 보낸 것처럼 보이는 말풍선 추가
- `st.chat_input()`으로 진짜 사용자 입력창 추가 → 사용자가 뭔가 입력하면 그 값이 `user_input`에 문자열로 저장됨
- `if user_input:` 으로 "입력이 있을 때만" 그 내용을 사용자 말풍선으로 표시

**⚠️ 발견된 버그 (다음 단계에서 고쳐질 가능성 높음, 표시만 해둠)**
```python
st.markdown("user_input")   # 따옴표 안에 그대로 있어서 "user_input"이라는 글자 자체가 출력됨
```
→ 변수 `user_input`을 표시하려면 따옴표 없이 `st.markdown(user_input)`이라고 써야 함. 지금 코드대로면 사용자가 뭘 입력하든 항상 "user_input"이라는 고정 텍스트만 화면에 뜸.

### 4단계 — 따옴표 버그 수정

```python
if user_input:
    with st.chat_message("user"):
        st.markdown(user_input)   # 따옴표 제거 → 진짜 변수값이 출력되도록 수정
```
> 3단계에서 짚었던 버그 그대로 수정됨. 이제 사용자가 입력창에 친 내용이 그대로 말풍선에 표시됨.

**여기서부터 방향 전환**: 이제부터 "복붙해서 쓸 정도로 비슷한 코드들"을 별도 파일(모듈)로 분리하는 리팩토링을 진행할 예정. 아래 "🔄 리팩토링 판단 기록" 섹션에 단계별로 이전/이후 비교와 이유를 기록.

## 📘 문법 질문 모음

### Q1. "role이 상수, msg가 변수 — 이게 무슨 소리지?" (app.py 6단계 주석)

**답**: `import`할 때 색깔로 구분한 것에서 나온 코멘트로 보임 —
```python
from common.show import show_msg   #보라색은 함수
from common.constants import ROLE  #초록색은 상수
```
`ROLE`은 `enum.Enum`을 상속받은 **클래스**이고, `ROLE.user`, `ROLE.assistant`는 프로그램 실행 중 절대 값이 안 바뀌는 **고정된 값(상수)**임. `show_msg` 함수의 파라미터 `role`, `msg` 중에서:
- `role`에는 `ROLE.user` / `ROLE.assistant`라는 **정해진 몇 개의 값 중 하나만** 들어옴 → "상수적인 성격"
- `msg`에는 사용자가 입력하는 **매번 다른 텍스트**가 들어옴 → "변수적인 성격"

즉 "role이 상수, msg가 변수"라는 건, `role` 파라미터에 들어오는 값의 **종류 자체가 `ROLE.user`/`ROLE.assistant` 딱 두 가지로 고정**되어 있는 반면, `msg`는 **매번 완전히 새로운 값**이 들어온다는 걸 구분해서 표현한 말로 보임. 이 구분이 정확히 6단계에서 `role`만 `ROLE` enum으로 검증하고 `msg`는 그냥 자유로운 `str`로 놔둔 이유와 연결됨 — "값의 종류가 제한된 것(role)은 enum으로 강제하고, 자유로운 것(msg)은 그냥 타입 힌트만 준다."

### Q2. `st.session_state`는 뭐고, 왜 일반 변수 대신 이걸 쓰는가

**참고 — 7단계에서 발견했던 문제**: Streamlit은 사용자가 뭔가 입력할 때마다 `app.py` **스크립트 전체를 처음부터 다시 실행**하는 구조라서, 일반 파이썬 변수(예: `history = []`)로 저장하면 스크립트가 재실행될 때마다 그 변수가 다시 빈 리스트로 초기화되어버림.

`st.session_state`는 Streamlit이 제공하는 **특별한 저장 공간**으로, **스크립트가 몇 번을 재실행되든 그 값이 유지**되도록 설계되어 있음 (사용자가 브라우저 세션을 유지하는 동안 계속 살아있음). 일반 변수는 8/11~8/12에 배운 것처럼 "코드가 다시 실행되면 초기화"되지만, `st.session_state`에 넣어둔 값은 Streamlit이 별도로 관리해서 재실행 사이에도 안 사라짐 — 딕셔너리처럼 `st.session_state.history`, `st.session_state['history']` 형태로 키를 붙여서 원하는 값을 저장/조회할 수 있음.

## 🔄 리팩토링 판단 기록

> 강사님이 "이렇게 바꾸면 되죠?"하면서 코드를 고친 부분들. 이전 버전 → 이후 버전을 비교하고, 왜 바꿨는지 이유를 판단해서 기록.

### 리팩토링 1 — 반복되는 `with st.chat_message + st.markdown` 패턴을 함수로 분리

**이전 (3~4단계)**
```python
with st.chat_message("user"):
    st.markdown(user_input)

with st.chat_message("assistant"):
    st.markdown("코딩이 그렇게 좋아?")
```

**이후 (5단계)**
```python
# common/show.py
def show_msg(role:str, msg:str) -> None:
    with st.chat_message(role):
        st.markdown(msg)

# app.py
show_msg(role="user", msg="코딩 너무 좋아")
show_msg(role="assistant", msg="코딩이 그렇게 좋아?")
```

**왜 바꿨는가 (판단)**
- `with st.chat_message(역할): st.markdown(내용)`이라는 **똑같은 두 줄 패턴**이 "user"일 때도, "assistant"일 때도 계속 반복되고 있었음. 유일하게 다른 건 "역할(role)"과 "내용(msg)" 두 가지뿐.
- 이렇게 **"구조는 완전히 같고 값만 다른" 코드가 반복될 때가 함수로 뽑아내야 하는 전형적인 신호**. 8/11에 배운 "함수를 쓰는 이유 = 반복적인 프로그래밍을 피하기 위해"가 정확히 여기 적용됨.
- **함수 vs 클래스 선택**: 강사님이 주석으로 직접 남긴 판단 기준 그대로 — "함수 안의 변수를 기억해야 하면 클래스, 아니면 함수". `show_msg`는 메시지를 화면에 찍고 나면 그 값을 더 이상 기억할 필요가 없는(호출 한 번으로 끝나는) 동작이라 **함수로 충분**하다고 판단함. 이건 8/12에 다뤘던 "함수 vs 클래스 선택 기준(여러 개의 독립적인 상태를 유지해야 하는가)"과 정확히 같은 논리.
- **별도 파일(`common/show.py`)로 분리한 이유**: "복붙해서 쓸 정도로 비슷한 것들"을 한 파일에 모아두면, 나중에 다른 파일(예: 다음에 만들 `common/history.py` 등)에서도 `from common.show import show_msg`로 가져다 쓸 수 있음. 8/12에 배운 모듈화 개념(재사용을 위해 `.py` 파일로 분리) 그대로 적용된 것.

### 리팩토링 2 — `role`을 문자열("user"/"assistant") 대신 `ROLE` enum 객체로 바꾸고, 검증 로직 추가

**이전 (5단계)**
```python
def show_msg(role:str, msg:str) -> None:
    with st.chat_message(role):
        st.markdown(msg)

show_msg(role="user", msg="코딩 너무 좋아")
```

**이후 (6단계)**
```python
# common/constants.py
class ROLE(enum.Enum):
    user = enum.auto()
    assistant = enum.auto()

# common/show.py
def show_msg(role:str, msg:str) -> None:
    assert isinstance(role, ROLE), "정상적인 코드가 아닙니다."
    with st.chat_message(role.name):
        st.markdown(msg)

# app.py
show_msg(role=ROLE.user, msg="코딩 너무 좋아")
```

**왜 바꿨는가 (판단)**
- **문자열 방식의 문제점**: `role="user"`처럼 그냥 문자열을 넘기면, 누군가 실수로 `role="유저"`나 `role="User"`(대소문자 오타)처럼 잘못 입력해도 **파이썬은 이걸 막을 방법이 없음**. 오타가 나도 에러가 안 나고 조용히 잘못된 동작을 하다가, 나중에 `st.chat_message()`가 "이런 역할 몰라요"라며 엉뚱한 곳에서 에러를 냄 — 원인 파악이 오래 걸림.
- **`ROLE` enum + `assert isinstance(...)`로 바꾼 이유**: `role`이 반드시 `ROLE.user` 또는 `ROLE.assistant`라는 **정해진 값 중 하나**여야만 함수가 실행되도록 강제함. 오타나 잘못된 값이 들어오면 `show_msg` **호출 시점에 바로** `AssertionError`가 나서, 문제가 어디서 생겼는지 즉시 알 수 있음. 이건 8/12에 배운 클래스의 `p_name if p_name is not None else "없음"` 같은 **방어적 프로그래밍**과 같은 맥락 — "값이 들어오는 시점에 미리 걸러내서, 나중에 엉뚱한 곳에서 터지는 걸 막는다."
- **`role.name`을 쓰는 이유**: `ROLE.user`는 객체 자체라서 `st.chat_message()`에 바로 넣을 수 없고, `st.chat_message()`는 문자열이 필요함. `role.name`으로 `ROLE.user` → `"user"`라는 실제 텍스트 이름을 꺼내서 넘겨줌 (8/12에 다룬 enum의 `.name` 속성 활용).
- **app.py에서는 `ROLE.user.name`이 아니라 그냥 `ROLE.user`를 넘기는 이유** (앱 코드 주석에 본인이 이미 적어둔 판단): 검증 로직(`isinstance` 체크)이 `show.py` 쪽에 있기 때문에, 문자열이 아니라 **객체 자체**를 넘겨야 그 객체가 진짜 `ROLE`의 멤버인지 검사할 수 있음. 미리 `.name`으로 문자열로 바꿔서 넘기면, `show_msg` 입장에서는 그게 원래 `ROLE`에서 나온 값인지 그냥 아무 문자열인지 구분할 수 없어져서 검증 자체가 무의미해짐.

### 리팩토링 4 — `history` 재초기화 방지 조건 추가 + append로 실제 누적 저장 구현

**이전 (8단계)**
```python
st.session_state.history = [
    {"role": ROLE.user, "msg": "코딩 너무 좋아"},
    {"role": ROLE.assistant, "msg": "나도 좋은가?"}
]
# → 스크립트 재실행마다 이 줄이 다시 실행되어 매번 초기화됨. append하는 코드도 없음.
```

**이후 (9단계)**
```python
if "history" not in st.session_state:
    st.session_state.history = []

# ... 입력이 들어오면
st.session_state.history.append({"role": ROLE.user, "msg": user_input})
show_msg(**st.session_state.history[-1])
```

**왜 바꿨는가 (판단)**
- 근본 원인은 **"변수 선언은 곧 초기화"**라는 파이썬 기본 규칙이 Streamlit의 "입력마다 전체 재실행" 구조와 충돌한 것. `if "history" not in st.session_state:`로 감싸서, **최초 1회만 초기화되고 그 이후 재실행에서는 이 줄 자체가 건너뛰어지도록** 만들어 문제를 해결.
- `append()` + `[-1]` + `**` 언패킹 조합으로, "저장"과 "화면 표시"를 분리하지 않고 한 번에 처리 — 저장한 직후 바로 그 항목을 꺼내 그리는 방식이라 코드 흐름이 직관적임.

### 리팩토링 7 — 가짜 AI 응답(`ai.py`)을 진짜 GROQ API 호출로 교체 (챗봇 핵심 기능 완성)

**이전 (11단계)**
```python

    return user_input + "*"*5
```

**이후 (15단계)**
```python
@st.cache_resource
def get_client():
    load_dotenv()
    return Groq()

def get_msg_of_ai(user_input:str, model_name:str="openai/gpt-oss-120b") -> str:
    messages = [
        {"role": h['role'].name, "content": h['msg']}
        for h in st.session_state.history
    ]
    messages.append({"role": ROLE.user.name, "content": user_input})

    client = get_client()
    response = client.chat.completions.create(messages=messages, model=model_name)
    return response.choices[0].message.content
```

**왜 바꿨는가 (판단)**
- 11단계에서 이미 "인터페이스(문자열 받아서 문자열 리턴)는 고정해두고, 내부 구현만 나중에 진짜 AI로 교체하기 쉽게" 설계해뒀던 의도가 이번 단계에서 정확히 실현됨. `app.py`, `show.py`, `history.py`, `constants.py`는 이번 교체 과정에서 **단 한 줄도 안 바뀜** — `ai.py` 파일 하나만 내부 구현을 갈아끼운 것.
- 대화 이력을 "저장용 형식"과 "API 요청용 형식"으로 분리해서 관리한 것도 핵심 설계 판단: `st.session_state.history`에는 계속 우리 프로젝트에 맞는 형식(`msg`, `ROLE` 객체)으로 저장해두고, GROQ에 보낼 때만 그 순간에 필요한 형식(`content`, 문자열)으로 변환. 저장 형식을 API 형식에 맞춰 처음부터 다르게 설계했다면, 나중에 다른 AI 서비스(OpenAI 등)로 바꿀 때 저장된 과거 데이터 전체를 마이그레이션해야 하는 문제가 생겼을 것.
- `@st.cache_resource`로 GROQ 연결을 싱글턴화한 것은 8/12에 직접 구현했던 싱글턴 패턴(metaclass 방식)을, Streamlit이라는 특정 프레임워크 환경에서는 훨씬 간단한 데코레이터 형태로 이미 제공하고 있다는 걸 실전에서 확인한 사례.

**🎉 이 시점에서 챗봇 서비스의 핵심 기능(대화 저장 + 화면 표시 + 실제 AI 응답)이 전부 완성됨.**

```python
    return response.choices[0].message.content
```

**⚠️ 스타일상 아쉬운 점 (동작엔 문제없음)**: 리스트 컴프리헨션의 반복 변수 이름을 `history`로 지었는데, `st.session_state.history`(전체 목록)와 이름이 겹쳐서 헷갈릴 수 있음. `for history in st.session_state.history`는 문법적으로는 문제없이 동작하지만(파이썬이 스코프 내에서 임시로 구분해줌), 가독성 측면에서 `msg`나 `h` 같은 다른 이름이 나을 수 있음.

**한 일 / 이유**

**① `@st.cache_resource`로 GROQ 클라이언트를 싱글턴화**
```python
@st.cache_resource
def get_client():
    load_dotenv()
    return Groq()
```
- Streamlit은 사용자가 뭔가 입력할 때마다 스크립트 전체를 재실행하는 구조라서, `get_client()`를 아무 처리 없이 부르면 **매번 새로운 GROQ 연결을 생성**하게 됨 — 비효율적이고 느림.
- `@st.cache_resource`는 8/12에 배운 **싱글턴 디자인 패턴**을 Streamlit이 데코레이터 한 줄로 구현할 수 있게 제공한 것 — "이 함수는 최초 1번만 실행하고, 이후엔 그때 만든 결과(연결 객체)를 계속 재사용해라." 8/12에 직접 `metaclass`로 힘들게 구현했던 싱글턴을, Streamlit 환경에서는 데코레이터 하나로 훨씬 간단히 적용할 수 있다는 걸 보여주는 사례.
- `load_dotenv()`: `.env` 파일에 저장해둔 `GROQ_API_KEY`를 파이썬이 읽을 수 있는 환경변수로 등록. `Groq()` 객체를 생성할 때 내부적으로 이 환경변수를 자동으로 찾아서 사용함.

**② 대화 이력(`history`)을 GROQ가 요구하는 형식으로 변환**
```python
messages = [
    {"role": history['role'].name, "content": history['msg']}
    for history in st.session_state.history
]
```
- `st.session_state.history`에 저장된 형식은 `{"role": ROLE.user, "msg": "..."}` (키 이름 `msg`, 값은 `ROLE` enum 객체)인데, GROQ API가 요구하는 형식은 `{"role": "user", "content": "..."}` (키 이름 `content`, 값은 순수 문자열)로 서로 다름.
- 그래서 **저장 형식(`msg`, 객체)과 API 요청 형식(`content`, 문자열)을 분리해서 관리**하고, 필요할 때 이렇게 변환해주는 구조. `role.name`으로 enum 객체에서 실제 문자열(`"user"`, `"assistant"`)을 꺼내는 방식은 6단계에서 이미 배운 것과 동일.
- **현재 사용자 입력까지 마지막에 추가**: `st.session_state.history`에는 아직 저장 전인 "방금 사용자가 친 메시지(`user_input`)"를 `messages` 리스트 맨 끝에 별도로 붙여서, **과거 대화 전체 + 지금 막 물어본 것**까지 한 번에 GROQ에 전달함. 이렇게 해야 AI가 이전 맥락을 기억하면서 답변할 수 있음.

**③ 실제 GROQ 호출 및 응답 추출**
```python
client = get_client()
response = client.chat.completions.create(messages=messages, model=model_name)
return response.choices[0].message.content
```
- `model_name`을 함수 파라미터로 받되 **디폴트값**(`"openai/gpt-oss-120b"`)을 지정해둬서, 이 함수를 지금까지 쓰던 대로 `get_msg_of_ai(user_input)`처럼 인자 하나만 넘겨도 그대로 동작함 (8/11에 배운 디폴트 파라미터 원칙 그대로 — 기존 호출 코드를 하나도 안 바꿔도 되도록 설계).
- `response.choices[0].message.content`: GROQ 응답은 여러 개의 답변 후보(`choices`)를 담을 수 있는 구조라서, 그중 첫 번째의 실제 텍스트 내용만 뽑아서 리턴함.

**결과**: 11단계까지 `user_input + "*"*5`였던 가짜 AI 응답이, 이번 단계로 **진짜 GROQ LLM이 생성한 응답**으로 완전히 교체됨. `app.py`나 다른 모듈은 전혀 안 건드리고 `ai.py` 내부 구현만 갈아끼운 것 — 11단계에서 판단했던 "인터페이스는 고정, 내부 구현만 나중에 교체 가능하게" 설계 의도가 정확히 실현됨.

**한 일 / 이유**

**핵심 변화**: 지금까지는 `app.py`에서 `history.append(...)` → `show_msg(**history[-1])` 이렇게 **"저장"과 "표시"를 두 줄로 나눠서** 직접 처리했는데, 이제는 `show_msg()` **함수 안에서 두 가지를 한 번에** 처리하도록 바뀜. `app.py` 쪽 코드는 그만큼 짧아지고, "저장 로직을 신경 쓰지 않고 그냥 show_msg만 부르면 알아서 다 된다"는 형태가 됨.

**`is_history` 파라미터를 넣은 이유** (본인이 코드에 직접 남긴 판단): "history가 부를 때랑 app이 부를 때랑 로직이 달라야겠지? 안 그럼 두 번 저장하게 되니까." →
- **`app.py`에서 부를 때**(새 대화가 막 생겼을 때): `is_history` 기본값 `False` → 화면에 그리는 **동시에 history에도 새로 저장**해야 함
- **`history.py`(`init_history`)에서 부를 때**(이미 저장되어 있던 과거 대화를 화면에 다시 그릴 때): 이미 `st.session_state.history` 안에 있는 걸 꺼내서 그리는 것뿐이므로, **또 저장하면 중복**됨 → `is_history=True`로 넘겨서 저장 로직을 건너뛰게 해야 함

**왜 이렇게 바꿨는가 (판단)**
- 이전 구조(9~11단계)에서는 "저장하고, 그 저장된 것을 다시 꺼내서 그리는" 2단계 과정을 `app.py`에서 매번 반복해서 써야 했음. 근데 사실 "메시지 하나가 생기면, 저장하고 그린다"는 건 **거의 항상 같이 일어나는 동작**이라서, 이 둘을 하나의 함수 책임으로 합치는 게 자연스러움.
- 대신 "이미 저장된 걸 다시 그리기만 할 때"(=`init_history`가 화면을 복원할 때)는 저장 로직이 필요 없는 **예외 상황**이라서, 이 경우만 `is_history=True`라는 플래그로 구분해서 저장을 건너뛰게 만든 것. 8/11에 배운 **디폴트 파라미터**(`is_history=False`)를 활용해서, 대부분의 경우(app.py에서 새 메시지 표시)엔 아무 값도 안 넘겨도 되고, 예외적인 경우(history 복원)에만 `True`를 명시적으로 넘기도록 설계.

**⚠️ 아직 남아있는 문제 (본인이 이미 정확히 예측한 그 문제)**
```python
# history.py
for h in st.session_state.history:
    show_msg(**h)   # is_history=True가 빠져있음!
```
`init_history()`에서 기존 대화를 화면에 복원할 때, `is_history=True`를 안 넘기고 있어서 **기본값 `False`가 적용**됨. 즉 스크립트가 재실행될 때마다, "이미 저장돼 있던 대화"를 또 `history`에 append하게 되어 **대화가 중복으로 계속 쌓이는 문제**가 생길 것으로 예상됨. 본인이 `show.py` 주석에 이미 "이렇게 하면 두 번 저장하게 된다"고 정확히 짚어놨는데, `history.py`에서 실제로 그 플래그를 넘기는 걸 아직 안 한 상태 — 다음 단계에서 `show_msg(**h, is_history=True)`로 수정될 것으로 예상.

**왜 바꿨는가 (판단)**
- 6단계까지는 "화면에 메시지가 잘 뜨는지"를 확인하기 위한 **테스트용 하드코딩 메시지**("코딩 너무 좋아" 등)가 있었음. `ROLE`/`show_msg` 조합이 정상 동작하는 걸 확인했으니, 이제 그 테스트 코드는 지우고 **실제 챗봇 흐름**(사용자가 입력하면 → AI가 응답)만 남긴 것.
- AI 응답(`msg='너무 좋아'`)은 아직 진짜 AI를 연결하기 전이라 **임시 고정 응답**으로 넣어둔 것으로 보임 (다음 단계에서 실제 AI 응답 함수로 교체될 가능성 높음).

**⚠️ 여기서 발견된 새로운 문제 (본인 메모 그대로)**
> "사용자가 어떤 멤시지를 이력할때마다 이전 메시지가 사라짐... 왜 사라지나? 기억하는 곳이 없음. 어딘가에 기억하고 show_msg를 통해 프린팅을 하면 계속 남아있음."

→ Streamlit은 사용자가 뭔가 입력할 때마다(`chat_input`에 입력이 들어올 때마다) **`app.py` 스크립트 전체를 처음부터 다시 실행**하는 구조. 그래서 이전 대화 내용을 어딘가에 **별도로 저장해두지 않으면**, 새로 입력할 때마다 화면이 리셋되고 방금 친 것만 보이는 것. 8/11~8/12에 배운 scope 개념과 연결됨 — 지금 코드에는 대화 내용을 계속 "기억"하는 곳이 없어서(함수 실행이 끝나면 지역변수처럼 사라짐), 이 문제를 해결하려면 **"기록을 계속 유지하는 저장소"**가 필요함. 다음 단계에서 이 문제를 해결하는 코드(`common/history.py` 등)가 나올 가능성 높음.

### 8단계 — `st.session_state`로 대화 기록을 저장해보는 첫 시도 (⚠️ 아직 미완성, 아래 참고)

```python
import streamlit as st

from common.show import show_msg #보라색은 함수
from common.constants import ROLE #초로색은 상수

st.title("ChatBot Service") #서비스 제목

st.session_state.history = [ #history는 리스트가 가장좋음. set은 중복답변 지워ㅓ릴수있으니 안되고, dict는 키를 계속 생성해줘야하니깐 굳이임. 튜플은 추가(수정)이 안됨. 바로 오류남. 그래서 리스트 써야함.
    {
        "role" :ROLE.user,
        "msg" : "코딩 너무 좋아"

    },
    {
        "role" :ROLE.assistant,
        "msg" : "나도 좋은가?"
    }
    #그 안에 role이랑 msg를 담아야하는데 딕셔너리형식으로 하느네 좋음. 명확하게 구분해야하는데 가장 좋은방법이 dict임
] #여기에다 기억하면 됨.(아래에서 어디에 기억하냐는거에 대한 대답)
#여기까지만하면 화면에 프린트는 안됨.
for h in st.session_state.history:
    show_msg(role=h['role'], msg=h['msg'])

#사용자 답변
user_input = st.chat_input("매시지를 입력해주세요.") #chat_input은 사용자의 답변을 str로 리턴해줌

if user_input: #user_input이 있다면
    #사용자
    show_msg(role=ROLE.user, msg = user_input)
    #AI
    show_msg(role=ROLE.assistant, msg='너무 좋아')
    #사용자가 어떤 멤시지를 이력할때마다 이전 메시지가 사라짐...
    #왜 사라지나? 기억하는 곳이 없음. 어딘가에 기억하고 show_msg를 통해 프린팅을 하면 계속 남아있음.
```

**한 일 / 이유**
- `st.session_state`라는 Streamlit 전용 저장소에 대화 기록을 담아보기 시작함 (7단계에서 발견한 "대화가 사라지는 문제"의 해결 시도)
- `history`는 **리스트**로 결정 — 본인이 남긴 판단 이유 그대로:
  - `set`(집합) 안 되는 이유: 중복된 답변이 자동으로 지워질 수 있음 (같은 말을 두 번 하면 하나가 사라짐 — 대화 기록에선 절대 안 됨)
  - `dict`(딕셔너리) 굳이 안 쓰는 이유: 대화가 늘어날 때마다 키를 계속 새로 만들어줘야 해서 번거로움
  - `tuple`(튜플) 안 되는 이유: 불변이라 새 대화를 추가(수정)할 수 없음, 시도하면 바로 에러
  - → 그래서 **추가(append)가 자유롭고, 순서가 유지되고, 중복도 허용되는 리스트**가 정답
- 리스트 안의 각 대화 한 마디는 **딕셔너리**(`{"role": ..., "msg": ...}`)로 구성 — "role과 msg를 명확히 구분해서 담기에 가장 좋은 방법"이라는 본인 판단. 이건 8/12에 배운 "언제 리스트, 언제 딕셔너리"(의미를 명확히 하고 싶을 때 딕셔너리) 원칙과 정확히 일치.
- `for h in st.session_state.history:`로 저장된 대화 목록을 순회하면서 `show_msg`로 하나씩 화면에 그려줌

**⚠️ 아직 미완성인 이유 (다음 단계에서 고쳐질 것으로 예상)**
1. `st.session_state.history = [...]`가 **매번 스크립트가 재실행될 때마다 새로 초기화**됨. 즉 지금 코드는 여전히 "고정된 2개짜리 예시 대화"로 **매번 리셋**되고 있어서, 진짜 "누적 저장"은 아직 안 되고 있음. (아마 다음 단계에서 "이미 history가 있으면 초기화하지 않기" 같은 조건이 추가될 것으로 예상)
2. `if user_input:` 블록 안에서 사용자의 새 메시지를 `st.session_state.history`에 **추가(append)하는 코드가 없음** — 그냥 `show_msg`로 화면에 찍기만 하고, 저장소에는 안 넣고 있어서 다음 재실행 때 역시 사라질 것으로 보임.

### 9단계 — history 중복 초기화 방지 + 대화를 실제로 누적 저장하도록 완성

```python
import streamlit as st

from common.show import show_msg #보라색은 함수
from common.constants import ROLE #초로색은 상수

st.title("ChatBot Service") #서비스 제목


#이력데이터를 저장하기 위해서 아래 변수를 선언한거임.
#선언! => 초기화. 그래서 메시지를 아무리 입력해도 초기화되는거임.
#그러므로 history에 데이터가 있다면 초기화하지 말아줘라고 해야함.
if "history" not in st.session_state:

    st.session_state.history = [ #history는 리스트가 가장좋음. set은 중복답변 지워ㅓ릴수있으니 안되고, dict는 키를 계속 생성해줘야하니깐 굳이임. 튜플은 추가(수정)이 안됨. 바로 오류남. 그래서 리스트 써야함.

    ]


for h in st.session_state.history:
    show_msg(role=h['role'], msg=h['msg'])

#사용자 답변
user_input = st.chat_input("매시지를 입력해주세요.") #chat_input은 사용자의 답변을 str로 리턴해줌

if user_input: #user_input이 있다면
    #사용자
    st.session_state.history.append(
        {
            "role":ROLE.user,
            "msg":user_input
        }
    )
    show_msg(**st.session_state.history[-1])
    #AI
    st.session_state.history.append(
            {
                "role":ROLE.assistant,
                "msg":"너무 좋아"
            }
        )

    show_msg(**st.session_state.history[-1])
    #사용자가 어떤 멤시지를 이력할때마다 이전 메시지가 사라짐...
    #왜 사라지나? 기억하는 곳이 없음. 어딘가에 기억하고 show_msg를 통해 프린팅을 하면 계속 남아있음.
```

**한 일 / 이유**

**① 초기화 문제 해결**
```python
if "history" not in st.session_state:
    st.session_state.history = []
```
- `in` 연산자로 `st.session_state` 안에 `"history"`라는 키가 **이미 있는지 먼저 확인**. 없을 때만(즉 맨 처음 딱 한 번만) 빈 리스트로 초기화하고, 이미 있으면(=재실행이라 이전 대화가 저장돼 있는 상태면) 이 블록 자체를 건너뛰어서 **기존 데이터를 그대로 보존**함.
- 본인이 직접 정리한 원리: "선언! => 초기화. 그래서 메시지를 아무리 입력해도 초기화되는 거임." → **"변수 선언 = 그 순간 무조건 초기화"**라는 파이썬의 기본 동작을 정확히 짚어낸 것. 이걸 막으려면 "이미 있으면 다시 선언하지 않는다"는 조건이 필요하다는 결론까지 스스로 도달함.

**② 실제 저장(append) 로직 추가**
```python
st.session_state.history.append({"role": ROLE.user, "msg": user_input})
show_msg(**st.session_state.history[-1])
```
- 8단계까지는 `show_msg`로 화면에 찍기만 하고 저장소엔 안 넣었는데, 이번엔 **`append()`로 리스트에 실제로 추가**한 다음, 방금 추가한 마지막 항목(`[-1]`)을 꺼내서 화면에 그림.
- `show_msg(**st.session_state.history[-1])`: 8/11에 배운 **가변 키워드 파라미터(`**kwargs`) 펼치기** 활용. `history[-1]`은 `{"role": ..., "msg": ...}`라는 딕셔너리인데, `**`을 붙이면 `show_msg(role=..., msg=...)`처럼 **딕셔너리의 키를 파라미터 이름에, 값을 파라미터 값에 자동으로 매칭**시켜서 넘겨줌. 딕셔너리를 굳이 `h['role']`, `h['msg']`로 하나씩 꺼내서 넘길 필요 없이 한 번에 넘길 수 있어서 코드가 짧아짐.
- AI 응답(`"msg": "너무 좋아"`)도 똑같은 방식으로 저장 → 이제 사용자 메시지와 AI 응답 둘 다 `history`에 순서대로 쌓이고, 다음에 스크립트가 재실행돼도(①번 덕분에) 안 사라지고 `for h in st.session_state.history:` 루프가 전부 다시 그려줌.

**결과**: 드디어 대화가 누적되어 계속 화면에 남아있게 됨. 7~8단계에서 발견했던 "메시지가 사라지는 문제"가 완전히 해결됨.

**⚠️ 남은 미완성 포인트**: AI 응답이 여전히 `"너무 좋아"`로 **고정된 하드코딩 값**임. 실제 AI(GROQ API로 추정, pyproject.toml에 `groq` 라이브러리가 있었음)와 연결하는 건 다음 단계에서 진행될 것으로 예상.

```python
import streamlit as st
from common.show import show_msg

#여기서는 함수, 클래스 뭐써야함?
#함수!! 왜 ? 기억해야하는거아님? no
# 이미 session_state요놈이 서버에 저장하고있음.


def init_history()->None:
    if "history" not in st.session_state:

        st.session_state.history = [ #history는 리스트가 가장좋음. set은 중복답변 지워ㅓ릴수있으니 안되고, dict는 키를 계속 생성해줘야하니깐 굳이임. 튜플은 추가(수정)이 안됨. 바로 오류남. 그래서 리스트 써야함.

        show_msg(**h)
```

**한 일 / 이유 (버그 부분 제외)**
- 9단계에서 `app.py` 맨 위쪽에 있던 "history 초기화 + 기존 대화 화면에 그리기" 로직을 `common/history.py`의 `init_history()` 함수로 통째로 옮김
- **함수 vs 클래스 판단** (본인이 코드에 직접 남긴 판단): "여기서 뭘 써야 함? 함수! 왜? 기억해야 하는 거 아님? → no, 이미 `session_state`가 서버에 저장하고 있음." → 8/12에 배운 "클래스는 데이터를 계속 기억해야 할 때 쓴다"는 원칙을 정확히 적용한 판단. `init_history()`가 다루는 대화 데이터(`history`)는 함수 자신이 기억하는 게 아니라 **`st.session_state`라는 이미 존재하는 별도의 저장소**가 대신 기억해주고 있으므로, 함수는 "그 저장소를 조회/초기화하는 동작"만 하면 되고 자기 자신이 상태를 유지할 필요가 없음 → 그래서 클래스가 아니라 함수로 충분.
- **왜 별도 파일로 분리했는가**: `app.py`가 "화면에 뭘 보여줄지"에만 집중하도록 하고, "대화 기록을 어떻게 관리할지"는 별개의 관심사로 분리한 것 — 8/12에 배운 모듈화 원칙("복붙해서 쓸 정도로 비슷한 것들"이 아니더라도, **역할이 명확히 다른 로직은 파일 단위로 나누는 것**도 좋은 구조화 방식) 그대로 적용.
